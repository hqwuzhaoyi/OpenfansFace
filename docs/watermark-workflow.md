# 水印识别与归名操作记录

适用于抽样扫描待分类视频、人工校正账号、按已确认名单归名，以及复查未检出的文件。启动方式见 [README](../README.md#水印识别)，抽帧、聚合和账号解析以 [watermark_worker.py](../maintenance/watermark_worker.py) 为准。

## 2026-11-06 实测

当时待分类清单共 3,227 个文件。本轮从 100 个不同文件夹各取一个，共 100 个；选择偏向无脸记录及较小文件，其中 57 个没有人脸记录。

| 观测项 | 结果 |
| --- | ---: |
| 成功读取的采样帧 | 800 |
| 检出重复文字的文件 | 79 |
| 有账号或署名候选的文件 | 53 |
| 仅频道、站点或其他文字的文件 | 26 |
| 未检出重复文字的文件 | 21 |
| 读取失败 | 0 |
| 账号字样 / 疑似署名 | 31 / 4 |

这些是按实际文件路径计数的样本结果，未做内容去重。一个文件可以出现多个账号，不能累加各账号的文件数来计算总量。79% 表示本轮重复文字检出率；本轮没有建立逐帧人工标注的真值集，不能据此报告人物分类准确率、召回率或全库覆盖率。

用户审核名单并授权分类后，51 个文件通过现有 API 归名并加入待归档；2 个多账号冲突文件保留待核对。原有 12 条队列记录逐项核对未变，执行后队列为 63 条。没有执行文件移动。21 个未检出文件全部保留，并交付播放地址、原始路径和采样时间；其播放端点均通过 `Range: bytes=0-0` 的 206 响应验证，该验证不证明全片解码或浏览器编码兼容性。

本轮使用了远端抽帧、本机 OCR 和独立报告。仓库中已实现水印后台、分组页面和接口，但本轮没有发布这些页面或启动生产常驻水印 worker。生产归名复用了已有的 `/api/plan/queue`。

## 页面接入（2026-11-06 后续）

后续已把功能发布为导航中的“提取水印”，入口 `/watermarks`；旧 `/unclassified/watermarks` 跳转到该入口。待分类页可以勾选视频直接提交任务。提取页面默认每批 20 个，可选择 10 / 20 / 50 / 100 个，展示后台进度及账号列表，支持最近一批、未检出、失败和来源筛选。

从结果组进入视频证据，每页最多 24 个文件，勾选仅作用于当前页。确认人物后复用待归档流程，来源记录为 `watermark`，撤销后返回提取水印页。后台以独立只读媒体容器运行，应用镜像为 `face-admin-next:v22-watermarks`，worker 镜像为 `face-watermarks:v1`。

本轮将首批扫描中 98 个仍匹配文件指纹的历史记录导入结果存储，保留原始 OCR，仅按当前解析器重新归并账号键；2 个变化记录跳过。已归名的视频由当前范围过滤，所以页面当时显示 49 个待处理文件的结果，其中 21 个未检出。历史报告中的人工截断校正没有自动变成全库别名规则。Telegram 账号字样保留为可撤销的来源标记。

发布验收包括 31 项 Node 测试、13 项 Python 测试、隔离接口回归、浏览器提取到归名与撤销流程、手机宽度检查，以及生产 worker 的单视频真实提取。发布前后队列内容逐字节一致。发布回执及回滚容器信息见项目经验入口中的本轮上线记录；后续状态以实时接口为准。

## 扫描与证据

1. 从实时 `/api/unclassified` 取得待分类范围，沿用当前文件路径解析、去重和已处理过滤。保存本轮 manifest：稳定视频 ID、路径、大小、纳秒修改时间、范围与抽样方法。
2. 无脸文件同样参与。先确认媒体可读取和可用计算资源；媒体所在机器资源紧张时，可只在那里抽帧，把 OCR 放到另一台有资源的机器。媒体只读，帧和结果写入独立任务目录。
3. 初扫使用 8 个分散时间点，覆盖约 2%～96% 的时长。全帧检测覆盖中央和移动水印，四角放大补充小字检测。实际模型、阈值和缩放参数读取 worker，不另维护一套默认值。
4. 每次抽帧前清理该次临时图片。FFmpeg 可能成功退出但未输出新帧，特别是在接近片尾时；旧图片不能算成新时间点的证据。
5. 同一帧的多个裁剪只算一票。当前聚合要求文字至少出现在两个不同采样帧，识别分数只衡量文字读数。
6. 保留原文、平台线索、时间点、不同帧数、识别分数、文字位置、证据截图和文件指纹。文件变化或管线版本变化时，缓存重新评估。

计算并行度按资源选择，不固定照搬本次进程数。多个 worker 分配互斥任务，或使用任务领取锁；只提交完整结果后再标记完成。中断后从已完成记录续跑，避免两个 worker 同时写同一份证据或删除对方的临时帧。

## 文字校正与人物判定

- 将作者账号、疑似署名、频道或站点来源、字幕或软件标志分开。识别到 Telegram 地址只证明画面有该来源线索。
- 账号解析支持完整平台 URL、`TG@`、`X:@`、`IG:@` 等形式；原文仍需保留。平台与完整账号共同确定身份线索，不能只靠去标点后的字符串合并。
- 从证据截图核对下划线、大小写、数字尾缀以及 `l` / `1` 等混淆。截图已截断时，回到该时间点的原帧扩大区域，不能猜测缺失字符。
- 将“原 OCR → 校正文字 → 证据 → 适用视频”一起记录。某段视频的局部截断被补全，不代表相同短前缀在全库都属于同一账号。
- 人物库精确同名可以作为候选；相近名字或不同平台的同名账号需要额外核对。一个视频含两个账号，不自动证明它们是同一人的别名。
- 对已经明确属于同一人的账号，优先复用现有人物名。尚未确定的多账号冲突保留待核对；频道来源不会转为人物归名规则。

## 按已授权名单归名

扫描请求产出候选名单。明确的分类请求可以执行其覆盖范围内的归名；原视频移动按现有待归档流程处理。授权和历史别名结论均绑定当次任务范围。

执行前生成具体计划：每个视频只对应一个目标人物，单列冲突和未检出项。保存队列及相关人工状态的备份。重新核对计划中每个文件仍在待分类范围，路径、大小和纳秒修改时间与 OCR 证据一致。

通过现有 `POST /api/plan/queue` 按人物提交，保留 `source`、本轮 `source_id` 和每批回执。网络中断导致结果未知时，先读回队列核实哪些视频已加入，再恢复剩余任务。复用 `DELETE /api/plan/queue` 撤销本次视频，避免用旧备份覆盖用户后来添加的操作。

完成标准：

- 所有计划成功归名的视频都在队列中，人物与计划一致。
- 执行前已有的队列记录逐项保持不变。
- 新增数量按视频 ID 去重核对，与本轮回执相符。
- 冲突项与未检出项仍可核对；报告区分“已加入待归档”和“已移动文件”。

## 未检出复查

先交付完整清单：原名单编号、播放地址、原始路径、时长、实际采样时间点。逐项检查地址可读取，并说明测试方式及其限制。

“未检出重复文字”至少有四种可能：画面没有水印、只短暂出现、文字难识别、识别到了但未达到跨帧重复阈值。保留这个状态，不直接标为“无水印”。

用户给出编号及出现时间或位置后，在对应区间增加采样、扩大或移动裁剪区域；复查单帧原始候选并标出与首轮过滤条件的关系。纯图形标志需要额外图像匹配，当前文字 OCR 结果不能排除它们。
