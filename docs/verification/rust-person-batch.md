# Rust 多人物合并与删除验收（#12）

`/api/persons/batch` 在显式 Rust 模式下转发至 `/v1/person-batch`；现有人物弹窗的双人／多人合并、单人／多人删除均使用该入口。Next 不执行该批次的媒体或账本变更，原生连接失败不会回退到旧执行器。历史旧批次仍可只读查询；未执行的旧批次在 Rust 模式下须重新预览。

## 持久化与恢复

- 父批次和全部原始子预览在现有 `operations` 表中一次提交，原始请求、子编号和版本不可换绑。`steps` 保存批次受理、当前人物和完成边界；不新增队列、数据库、执行线程或写入权威。
- 第一项取得自己的共享写锁后，先校验全部原始人物目录、文件指纹、相关本地记录和 Peach 账本。全部通过才持久化批次受理。该锁直接交给第一项原生执行器，不持有父锁再获取子锁。
- 每个人物是独立事务及补偿范围。后续人物在自己的写锁内重新规划目标冲突与共享资料，并与原始来源文件／稳定编号／目录身份核对。前项造成的同名冲突使用保留名；来源范围改变则停止。
- 子操作只能由绑定的父批次启动，不能借单人物 `preview/apply/reconcile` 路由提前执行。重复提交父编号与版本返回既有回执；剩余范围需要新预览和新编号。
- 启动时先按原生步骤恢复子操作，再汇总父批次。即使进程在子项提交与父项记录之间被 SIGKILL，也能从子回执恢复已完成范围，不重做成功人物，不自动启动尚未开始的人物。
- `POST` 的 `reconcile` 模式接受原 `id/version`，只核对已受理子项。每个存储域无法核对、真正不确定的文件系统变更、被改写的写锁均保留保护；确认已完成的人物不回滚。批次进度额外返回最终 `result` 与 `recovery_needed`。
- 日志 `user_version=5`：沿用 schema 4 的永久删除能力，新增批次状态语义和父子约束，因此旧执行器必须拒绝降级使用该日志；没有第二套批次 job 表。

现有弹窗保留真实视频预览、完整路径、直接播放、从已选人物指定保留对象和结果入口。删除现在也展示当前人物、已完成及尚未完成名单。原生预览没有提供的账号／待归档摘要不再显示为零。取消恢复原按钮焦点；结果改变了勾选导致原按钮消失或禁用时，关闭后聚焦刷新按钮。
